# 演示：三方基础地址拼写错误，可在开发本人确认后修复

这是本机模拟的修复手册，不代表公司生产策略。审核日期：2026-11-09。

```repair-policy
{"environments":["test"],"services":["order-service"],"keys":["partner.api.base-url"],"checks":["partner-status"],"publish":true}
```

适用现象：GET /api/partner/status 返回 PARTNER_CONNECT_FAILED，同一请求日志出现 UnknownHostException，且日志中的实际三方域名与 test 环境接入约定不同。

判断方法：查看关联请求日志和 PartnerClient 的配置读取逻辑；读取 PARTNER_API.md 的完整约定地址，再读部署配置的实际值。只有确认是该配置键地址拼写错误，且当前平台配置与故障日志一致时，才能提出修改。DNS、网络不通或未生效也可能导致类似现象，不能只凭异常类自动换地址。

允许的修复：可将 partner.api.base-url 从已经核实的错误值改成接入约定中的完整测试地址。具体旧值、新值由 Agent 读取现场及代码约定后提出，不从此授权块推导。必须先向开发本人展示版本、精确前后值、文档依据、发布目标和验证方法，再在 Harness 当前会话发起原生一次性审批；本人允许本方案后，才允许修改并发布到 test/order-service。群内发言或聊天文字不代替审批。

执行：调用平台的条件写入适配器，仅修改已确认的一个配置键并发布。不改其他环境、服务或配置键，不执行任意 SSH 命令或浏览器保存操作。若当前版本或文档变化，停止执行、重新提出方案并确认。

验证：选用平台支持的只读 partner-status 检查，同时核对保存配置、运行实例生效版本与新值。演示域名为 .invalid，仅验证模拟应用的状态请求，不会向外网发送请求。历史故障日志不能代替发布后的新验证。

失败处理：停止继续修改，报告保存/发布/验证的实际状态，保留原值、配置版本及操作编号。不要擅自回滚；如需要恢复原值，重新提出明确的恢复方案并由开发本人确认。
